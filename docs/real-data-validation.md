## P0/P1 优化回归

P0 提交 `347027b` 已重跑上述十五日、30 个日市场任务，全部语义报告与历史基线相等。
其冻结二进制 SHA256：
`0c46247747b49bac0da090fa749593ba6af5a24db9885599d6fcd3d167f04994`。
证据位于 `reports/20260909-p0-optimized-full-regression/`。

本次 P1 保持恢复和匹配规则不变，实施三项优化：

1. 候选先检查总量、加权价和成交统计。仅当标量差异已不可能改善最佳失败候选时，
   跳过十档读取；首次候选仍完整比较，收盘特殊规则仍完整检查。
2. 每个输入流缓存交易日零点，严格解析 `HH:MM:SS.mmm`；参考 Parquet 仅投影必要列，
   每个 RecordBatch 一次绑定 Arrow 类型，不逐行查列名／类型。
3. 参考十档以定长价量和 `u32` 委托数紧凑保存；失败诊断按需分配，匹配后释放。
   对外快照／报告格式及数量范围不变，参考委托数对应源数据 `UInt32`。

P1 以冻结 P0 为性能和结果基线，固定六进程并发、相同输入日期与运行参数。
独立证据目录为 `reports/20260909-p1-optimized-full-regression/`，运行结果见其
`manifest.json`、`summary.json`、`comparison.json` 及逐任务收据。
两批均省略成功逐帧明细；报告相等不等于逐条比较成功候选的时间和序号。
首次命中和最佳失败候选由差分测试逐候选对照完整比较路径验收。

2026-09-09 P1 全量回归已完成：30/30 任务通过，30 份 JSON 语义报告与 P0 完全相等。
414,714,148 个可比项全部匹配，553 个状态排除项不计入匹配；不匹配、数据错误及缺源均为零。
沪深各十五日的全部支持股票和 ETF 均在范围内，仍使用默认窗口和实用市价策略。

均下降。整批并发日历耗时从 137.95 分钟降至 102.66 分钟，不能与累计分项耗时混用。

评估结论：组合优化有效，主要观察到参考加载、输入处理和内存占用改善。
验证回调仍占 P1 validation 耗时的主要部分：本轮跳过 455,677,012 次十档读取，
实际构造 4,340,116,722 次，占二者之和的约 9.50% 被跳过。
保留最佳失败候选的保守剪枝不能跳过全部标量不匹配；回调仅有 22/30 个任务更快，
沪市累计仅改善 0.89%，深市改善 3.79%。因此回调收益应视为小幅变化，不能宣称稳定的
显著加速，也不能把组合收益独立归因于某一项优化；后续仍应重点分析未被跳过候选的构造与比较。

这些是相同六进程配置下的两批 instrumented wall time，并非独占 CPU 或多轮随机交错 A/B。
缓存、调度及系统负载会影响结果，不能据此承诺其他硬件的固定加速比。
本轮通过 130 项 all-target/all-feature 测试、默认 feature 测试、文档测试、严格 Clippy、
`cargo fmt --check` 及维护脚本的 Ruff 检查；新增差分、时间边界、紧凑存储和列绑定拒绝路径覆盖。

## Profiling

验证回调在恢复过程中执行，不能另跑 replay 后将两次总时间相减作为精确对比耗时。
默认生产 API 不记录运行耗时；启用 `profiling` 后，
`profile_validate_market_day` 返回同一次验证的分项时间：

```bash
cargo build --release --locked --features profiling --example validation_benchmark
target/release/examples/validation_benchmark \
  --date 20260320 --market SZ --temp-root target/profile-spool \
  --report reports/manual-profile-sz.json \
  --timings reports/manual-profile-sz-timings.json
```

此 example 与 CLI 的证券默认值不同：省略 `--symbols` 表示全部支持的股票与 ETF。
深市使用实用市价策略，不提供扩窗开关。`--max-detail-records` 默认 5000，0 表示不限；
不保留成功逐帧明细，全部汇总计数不受明细上限影响。请使用新的报告路径，不覆盖已有证据。

| 分项 | 范围 |
| --- | --- |
| `reference_load_seconds` | raw snapshot 读取、阶段检查和验证器初始化 |
| `input_spool_seconds` | 逐笔读取、Schema、过滤、通道分片及逆序修复 |
| `replay_excluding_validation_seconds` | 回放循环耗时扣除本次实际验证回调 |
| `validation_callbacks_seconds` | 候选盘口取值、字段比较和收盘审计 |
| `spool_cleanup_seconds` | 成功分片清理 |
| `report_finalize_seconds` | 验证汇总和报告构造 |
| `report_serialization_write_seconds` | benchmark 调用者写验证 JSON，位于核心计时之外 |
| `scalar_rejected_candidates` | 标量差异界限允许跳过十档读取的候选数（仅 profiling） |
| `depth_materializations` | 实际构造十档用于比较的候选数（包括收盘投影，仅 profiling） |

```text
恢复 = input_spool + replay_excluding_validation + spool_cleanup
对比 = reference_load + validation_callbacks + report_finalize
profiled_total = 恢复 + 对比 + unattributed
```

恢复不是纯 OrderBook::apply CPU 时间；这些都是 wall time，包含调度和资源争用。
时钟埋点有开销，不做未经实测的扣除。外层 `/usr/bin/time -v` 还包含进程启动、报告／
timing JSON 写出和退出；失败时不返回伪造的完整分项，保留进程耗时及失败上下文。

两批最多六进程并发，逐日恢复、对比、总耗时和峰值内存见各 summary。一天两市的跨度
取最早启动至最晚结束，不等于两市耗时相加；累计耗时是工作量，不能当作并发日历耗时。
数据规模、并发负载、缓存和埋点不同，不能直接归因于算法性能提升。
